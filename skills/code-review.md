# 代码审查

## 执行流程

### 第 1 步：确定审查范围

根据用户描述判断：
- 如果用户指定了**文件路径**，直接用 `read_file` 读取
- 如果用户指定了**commit 范围**（如 "最近 3 次提交"），用 `git_log` + `git_diff` 查看变更
- 如果用户**没有明确指定**，用 `git_diff` 查看工作区未提交的变更

### 第 2 步：逐文件分析

对每个文件从四个维度审查：

1. **正确性**
   - 逻辑是否有 bug
   - 边界条件是否正确处理（空输入、极端值等）
   - 是否有潜在的 null/None 引用问题
   - 异常处理是否完善

2. **性能**
   - 时间复杂度和空间复杂度是否合理
   - 是否有不必要的循环嵌套或重复计算
   - 数据结构选择是否恰当
   - 是否有可以缓存或延迟计算的优化机会

3. **代码风格**
   - 命名是否清晰反映意图
   - 函数是否过长（超过 50 行建议拆分）
   - 是否遵循项目现有的代码风格
   - 注释是否充分（关键逻辑必须有注释）

4. **安全性**
   - 是否有可能导致注入攻击的代码
   - API 密钥、密码等是否硬编码
   - 文件路径是否做了校验
   - 用户输入是否做了清理

### 第 3 步：输出审查报告

按以下格式输出：

```
## 📋 代码审查报告

### 审查范围
[说明审查了哪些文件/变更]

### 发现问题

#### 🔴 严重（必须修复）
| 文件:行号 | 问题 | 建议 |
|---|---|---|
| ... | ... | ... |

#### 🟡 警告（建议修复）
| 文件:行号 | 问题 | 建议 |
|---|---|---|
| ... | ... | ... |

#### 🔵 建议（可选优化）
| 文件:行号 | 建议 |
|---|---|
| ... | ... |

### 总体评价
[一两句话总结代码质量]
```
