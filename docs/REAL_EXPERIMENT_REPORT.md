# XClaw 真实模型对照实验报告

实验数据日期：2026-10-12；报告整理日期：2026-10-13。

## 实验完成情况

使用真实 DeepSeek API 完成 **24 个合成 Python 任务 × 4 种方案 × 3 次重复 = 288 条有效尝试**。
四种方案各 72 条，237 条通过独立验收，51 条任务失败。失败保留在分母中。
这些是受控任务集上的观测结果，不能作为生产环境成功率或真实仓库基准排名。

API 余额不足造成的 **200 条不可评价记录**单独归档，没有算作模型完成任务的失败。
另有 3 条中断调用链保留现场：2 条外部中断、1 条余额不足触发的并发取消。
补跑从原代码基线开始，保留同一任务、模型和预算。已完成且验收过的尝试没有重跑。

## 固定运行条件

| 项目 | 配置 |
|---|---|
| 模型 | deepseek-v4-pro |
| 任务集 | 10 个 bug 修复、6 个功能实现、4 个多文件任务、4 个历史约束任务 |
| 重复次数 | 每个任务、每种方案各 3 次 |
| 输入窗口 | 人为配置 8192 Token；使用字符/CJK 混合估算，不是官方 tokenizer |
| 单次输出上限 | 2048 Token |
| 主循环上限 | 12 轮；达到上限后的总结不算任务正常完成 |
| 任务超时 | 180 秒 |
| 独立任务并发 | 2，所有方案共用 |
| 工具并发上限 | 4；只有声明安全的只读工具可并发 |
| 模型采样 | 请求 temperature=0；主模型默认思考行为不保证确定性 |
| 辅助请求 | 摘要、调度、记忆的 DeepSeek 请求关闭思考模式 |
| 验收 | 另一个干净 Docker 容器，工作区与隐藏验收脚本只读 |
| 执行镜像 | sha256:4a79da4b92e5fd1d93e2651fb5c72eebc38b57a79ab159e04d9faca968bd0e19 |

主流程只注册文件工具和 Bash，关闭记忆提取。模型无法读取隐藏验收与参考实现。
成功需要运行时正常完成、独立测试通过、修改路径满足约束。
模型回复“完成”不能代替实际修改与验收。
耗时包含模型、辅助请求、工具调用及必要的执行容器启动；独立验收耗时单独记录。

## 全部结果

| 方案 | 通过/尝试 | 成功率 | 耗时中位数 | P95 | 平均已报告 Token/任务 | 用量完整 |
|---|---:|---:|---:|---:|---:|---|
| 摘要 + 串行 | 67/72 | **93.1%** | **17.37 s** | 48.55 s | 13,203 | 是 |
| 摘要 + 依赖调度 | 63/72 | 87.5% | 20.36 s | 51.00 s | 14,787 | 是 |
| 截断 + 串行 | 54/72 | 75.0% | 22.12 s | 66.74 s | 15,875 | 否 |
| 截断 + 依赖调度 | 53/72 | 73.6% | 18.48 s | 72.63 s | 16,062 | 是 |

Token 包含主模型、摘要和调度请求，按服务端返回的用量累加。
`binary_search / truncate_serial / 第2次` 有请求缺少用量，所以截断+串行的 Token 只为已知下界。
因此不把它与摘要+串行的 Token 差异写成精确的节省比例。
288 条正式记录共报告 **4,314,708 Token**；诊断实验、中断和不可评价请求另列，
这个数字不等于整个调试过程的账单消耗，也不能据此推断实际费用。

## 分类结果

每种方案的 bug 类有 30 次，功能类有 18 次，多文件和历史约束类各有 12 次。

| 方案 | bug 修复 | 功能实现 | 多文件修改 | 历史约束保留 |
|---|---:|---:|---:|---:|
| 摘要 + 串行 | 29/30 | 14/18 | 12/12 | **12/12** |
| 摘要 + 依赖调度 | 28/30 | 14/18 | 10/12 | **11/12** |
| 截断 + 串行 | 30/30 | 15/18 | 9/12 | **0/12** |
| 截断 + 依赖调度 | 29/30 | 14/18 | 10/12 | **0/12** |

历史约束任务有意把要求放在较早轮次，后续对话不重复这些要求。
截断方案丢掉了这些信息，常出现追问、反复探索或不满足早期约束的实现。
因此这里验证的是特定历史保留场景，不代表所有长上下文任务都有相同提升。

## 可以支持的结论

1. **在保持依赖调度条件相同时，摘要替代截断的成功率由 73.6% 提升至 87.5%，增加 13.9 个百分点。**
   平均已报告 Token 从 16,062 降至 14,787，下降 **7.9%**；这两组用量记录完整。
   相应耗时中位数增加约 10.2%，存在质量、用量与延迟之间的取舍。
2. 在串行条件下，摘要方案由 75.0% 提升至 93.1%，增加 18.1 个百分点。
   全部尝试的耗时中位数从 22.12 秒降至 17.37 秒，但其中包含失败任务，
   不把它直接表述为相同成功任务的响应速度提高。
3. **本任务集没有证明依赖调度能加速。** 在摘要条件下，调度方案的成功率低 5.6 个百分点，
   中位耗时高 17.2%，平均 Token 高 12.0%。仅比较双方均成功的 60 个配对尝试，
   调度方案总耗时仍高约 9.4%。独立文件读取很短，额外规划请求可能抵消并发收益。
   调度的依赖校验和副作用互斥仍有工程价值，性能收益需在更多慢 I/O 任务上验证。

这些是本次样本上的描述性差异，没有做显著性或因果结论；不要将其外推到生产任务。

## 51 个任务失败的复盘

以下按“轮次上限 → 末次主请求输出上限 → 其他验收失败”的优先顺序分组，避免重复计数：

| 观察到的失败特征 | 数量 |
|---|---:|
| 未命中轮次上限，末次主请求 finish_reason=length | 31 |
| 达到主循环轮次上限 | 15 |
| 有代码变更，但隐藏测试仍未通过 | 4 |
| 没有代码变更，且未命中前述特征 | 1 |

最值得下一步处理的是输出终止语义：当前主循环在没有 tool_calls 时可能把空回复当作完成。
独立验收已将相应任务判失败，但产品侧应显式识别 `finish_reason=length` 和空回复，
返回“输出预算耗尽/任务未完成”，并设计受限的继续生成策略。
提高输出上限或修改该策略会改变实验条件，应另起一轮实验，不能覆盖本次记录。
