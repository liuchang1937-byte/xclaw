# 日常工具调用的依赖验证（2026-10-30）

## 测什么

本次单独验证新增依赖调度，不重新运行完整 Coding Agent 任务。固定一批工具调用，让真实模型提出依赖，再通过生产调度器和执行路由运行工具，检查实际结果。文件场景使用项目已有 `read_file`、`write_file`、`edit_file`、`search_in_files`、`list_directory`、`deliver_file`；客户、政策、订单查询使用固定数据的本地模拟服务，不请求真实业务系统。

24 类场景，每类重复 3 次，串行和依赖调度各 72 次，共 144 次。每次独立工作区；任务间并发 1；交替两组执行顺序。使用当前配置模型 `deepseek-v4-pro`，调度 temperature=0，最多并行 4 个工具，规划超时 10 秒。每个实际工具体额外等待 20ms，使执行重叠可以稳定观测；因此这些延迟不能作为生产工具延迟或完整任务延迟。

串行组关闭模型调度，按原始调用顺序执行，仍保留代码固定的文件交付前置规则。许多用例故意将后继放到前置之前，属于依赖压力测试；串行失败比例不能推广为正常输入下的产品失败率。

必要依赖、期望返回值、文件终态、预期失败和延期由评测器持有，未放入调度模型消息。模型只能看到当前工具参数、工具说明与正常任务描述。依赖关系按传递闭包判断，不要求合法图具有完全相同的边集合。

## 判定规则

执行通过必须同时满足：

- 应执行的调用实际执行，禁止执行或延期的调用没有执行。
- 每条必要依赖都满足 `子调用开始 >= 父调用结束`，父调用失败时子调用不执行。
- 返回内容正确，最终文件内容正确，实际附件列表正确。
- 工具的预期失败被观察到，没有额外的意外失败。
- 独占工具不与任何工具重叠，最大并发不超过 4。
- 每个调用恰有一条结果，并按原始调用顺序回填。

“DAG 契约通过”还要求模型计划覆盖所有必要依赖。独立组是否发生重叠单独统计，避免保守串行被当作并发收益，也不把安全但保守的执行误判为数据错误。

## 执行器和评测器自检

新增 35 个确定性测试，与原有 34 个调度相关测试一起运行：**69 passed in 3.18s**。固定规划用于隔离模型随机性，工具与执行路由是真实实现。

负例覆盖：删除必要依赖仍输出合法 JSON、遗漏延期标记导致执行占位符、关闭调度后乱序消费者先执行。评测必须抓住这些错误。另验证传递依赖识别，避免只接受唯一图形。

## 实测结果

144/144 次完成。测试过程中保留模型失败，未改 Prompt、未调整生产调度、未补跑覆盖原始失败。72 次规划都正常返回，无降级，全部用量完整。

依赖调度组的执行通过与依赖契约通过均为 66/72。本次是特意加入乱序输入、前置故障和动态参数的工具批次压力集，**91.67% 不代表完整 Agent 任务成功率，25% 也不是普通串行的线上成功率**。串行组的 15 条关系覆盖来自现有文件交付固定规则。

依赖调度按类别统计：

| 类别 | 不同场景数 | 执行及契约通过 |
|---|---:|---:|
| 独立读取 | 3 | 9/9 |
| 文件顺序 | 9 | 21/27 |
| 查询顺序 | 4 | 12/12 |
| 文件检查与交付 | 2 | 6/6 |
| 故障处理 | 5 | 15/15 |
| 动态参数延期 | 1 | 3/3 |

故障处理的 15/15 包含前置失败阻断、独立任务不被取消及缺失文件的处理，不能泛化为所有异常恢复能力。实际 15 次工具错误均为预期故障，另有 18 次调用被正确跳过或延期。

性能仍受规划开销主导：工具很快，并且人为只加入 20ms 等待；本轮不能证明普通本地文件工具的净提速。独立组未并行的 3/27 次全部来自 `create_edit_check_fanout`：图正确地描述了创建与编辑的前置关系，但 `mode=serial` 让末端独立的读取和校验也顺序执行。它属于效率损失，执行正确性没有扣分。

## 已定位的问题

`edit_then_read_reversed`：用户要求将版本从 1 改为 2，再查看修改后的配置。必要关系是 `update → inspect`，模型却生成 `inspect → update`。结果读取返回 `revision=1`，最终文件虽然为 `revision=2`，仍判失败。

`two_edits_chain_reversed`：必要关系是 `review → approve → inspect`，模型将 `inspect` 提前到两次编辑之前。最终文件变为 approved，但读取结果仍是 draft。

两个场景均连续复现 3/3，共 6 次失败。所有失败的直接症状都是读取过早、返回旧内容；不是 API 异常、图结构非法、循环依赖或锁失效。最终文件正确也没有掩盖过程输出错误。

这两类失败都说明：计划格式合法、依赖无环、文件读写没有重叠，并不足以保证业务顺序正确。现有代码校验负责结构和互斥，没有识别“用户要修改前的检查，还是修改后的核验”的通用硬规则。

可优先优化调度 Prompt 与工具使用示例，明确区分修改前审查、修改后核验和旧新快照。不能简单给所有同路径读取都加“等待写入”的规则，那会破坏旧快照场景。若由主模型显式标注调用用途或依赖，可减少额外调度模型的语义猜测；优化后应在固定失败集和新增留出集同时验证。
